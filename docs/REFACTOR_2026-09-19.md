# EON AI Backend Simplification - 2026-09-19

## What changed

- Removed five thin Mastra workflow wrappers and `workflow-runner.ts`.
- Added `common.get_opportunity_intelligence` for broad internal opportunity summaries.
- Fine-grained CRM, FinOps, SharePoint, route, and web tools remain available for specific questions.
- Added `workflow.registry.ts` as the extension point for future workflow-native processes.
- Public chat API now uses `conversationId`; the backend derives Mastra `threadId` from it and derives `resourceId` from the authenticated user.
- Memory default reduced to the latest 8 messages.
- Agent defaults reduced to 12 steps and 6,000 maximum output tokens.
- Large tool outputs use Mastra `toModelOutput` compact projections.
- Sales instructions were reduced to source-of-truth, routing, evidence, missing-data, and output rules; capability selection lives primarily in tool descriptions.
- Local SearXNG results are deduplicated and snippets are capped at 700 characters.
- Stock inventory lookup is batched into one FinOps query per warehouse instead of one query per resolved item.
- MSDS lookup is batched for all resolved item numbers instead of repeating SharePoint list discovery per product.
- Generic tool lifecycle logging is centralized through Mastra agent hooks.
- Custom logs use `HTTP_REQUEST`, `HTTP_ERROR`, `AI_TOOL`, `AI_RUN`, and `INTEGRATION_ERROR` events.
- `/dev` keeps independent Local and Cloud conversations and shows backend duration, client wall time, steps, tokens, cached tokens, tools, sources, and web-search usage.

## Chat API

First request can omit `conversationId`:

```json
{
  "message": "Ringkas kondisi opportunity ini",
  "modelMode": "local",
  "context": {
    "opportunityId": "59cf2a22-6281-4465-9232-8ebeab009e5e"
  }
}
```

The response contains a generated `conversationId`. Send it on follow-up requests:

```json
{
  "message": "kalau stok yang kurang tadi yang mana saja?",
  "modelMode": "local",
  "conversationId": "<conversation-id-from-previous-response>",
  "context": {
    "opportunityId": "59cf2a22-6281-4465-9232-8ebeab009e5e"
  }
}
```

Clients should not send `resourceId`. A legacy `threadId` is accepted only as a temporary migration fallback.

## Adding a tool

1. Put source/business logic in `src/services/...` or a shared utility.
2. Create a thin Mastra tool under `src/mastra/tools/<namespace>/`.
3. Give it a precise capability-oriented `description` and Zod schemas.
4. Opportunity-bound tools use `opportunityRequestContextSchema` and `runOpportunityTool()`.
5. Large results define `toModelOutput` so the model sees only necessary fields.
6. Register it once in `src/mastra/tools/tool.registry.ts` and attach the relevant tool group to the agent that needs it.

Do not create a workflow for a single lookup/service call.

## Adding an agent

1. Create the agent in `src/mastra/agents/`.
2. Keep its instructions focused on role, source authority, evidence policy, and output behavior.
3. Select existing tool groups or specialist tools.
4. Register the agent in `src/mastra/agents/agent.registry.ts`.

`src/mastra/index.ts` and `src/mastra/runtime/agent.runner.ts` should not need agent-specific branches.

## Adding a workflow

Use `src/mastra/workflows/workflow.registry.ts` for processes that benefit from workflow semantics, such as branching, suspend/resume, approvals, retries, parallel deterministic steps, or long-running auditable processes. Register the workflow there; ordinary source lookups stay as services/tools.

## Defaults

```env
MASTRA_MEMORY_LAST_MESSAGES=8
LOCAL_AGENT_MAX_STEPS=12
CLOUD_AGENT_MAX_STEPS=12
AGENT_MAX_OUTPUT_TOKENS=6000
SEARXNG_MAX_RESULTS=5
SEARXNG_SNIPPET_MAX_CHARS=700
```
